title: Durability
description: "How KronosDB makes appended events durable with commit waves, and when an append is acknowledged."

An append is acknowledged once its events are durable, which means they survive a crash or power failure. This page describes how the server gets written records to that point with as few disk syncs as possible.

## Commit waves

Writing a record puts its bytes in the operating system's page cache, which does not survive a power failure. To make writes durable, the server groups them into commit waves. An append writes its records and joins the current wave. A sync thread closes the wave, calls `fdatasync` once for every record in it, and then moves the commit watermark past it. Appends that arrive while a sync is running join the next wave.

An append is acknowledged when the watermark passes its last event, and reads return only events below the watermark, so a client never reads an event that could still be lost. The size of a wave adjusts to the load: one append on an idle server gets a wave of its own, and under load each `fdatasync` covers many appends. There is no timer by default; `group-commit-ms` adds a wait before each sync.

In a cluster, the watermark is the position that a majority of the voters have reached, so an acknowledgement waits for that majority. Whether "reached" means written or synced is the `ack-mode` setting, described in [Configuration](/docs/kronosdb/configuration) and [Clustering and replication](/docs/kronosdb/replication).

## Disks that confirm writes early

When `fdatasync` returns, the disk has reported that the data is stored. Some disks report this while the data is still in a volatile write cache: drives without power-loss protection that have their write cache enabled, and some virtual and network disks. On such a disk, events acknowledged shortly before a power failure can be lost, and no software on that node can detect it. KronosDB uses the strongest sync each platform offers, `fdatasync` on Linux and `F_FULLFSYNC` on macOS, where a plain `fsync` does not empty the drive's cache, but no sync call makes a disk store what it has only confirmed. For data that must survive a power failure, use disks with power-loss protection, and check the [hardware findings](/docs/kronosdb/monitoring#check-the-hardware-findings) the server reports at startup.

Replication is what protects acknowledged events from a single disk like this. In a cluster, an append is acknowledged only after a majority of voters have it, so one node that loses its last writes in a power failure loses no acknowledged event. When that node starts, it cuts off any incomplete record at the end of its log, and when it rejoins, the leader sends it the events it is missing. Replication does not help when a majority of voters lose power at the same moment, so place voters where they do not share a power supply, a rack or a zone. A single node depends on its own disk alone.


An append that waits longer than the append deadline for its confirmation fails with `unavailable` and may still end up in the log. A client sends it again, and the server recognises the events and returns the positions they have, as [Events and tags](/docs/kronosdb/events-and-tags#retrying-an-append) describes. The deadline, `[timeouts] append`, is 20 seconds by default.

If a commit wave cannot be made durable, for example because `fdatasync` fails or the commit thread stops, the server cannot make the written events durable, so it stops accepting appends. Pending and later appends fail with `internal` and a message that the event store is poisoned, and the node accepts appends again after a restart.
