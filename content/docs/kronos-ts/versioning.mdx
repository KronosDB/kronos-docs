---
title: Versioning
description: How events change shape over time without rewriting the log, using event versions and upcasting.
---

Events are stored forever, so an event written last year is read by the code you deploy today. When the shape of an event changes, the stored events keep the old shape, and **upcasting** converts each one to the current shape as it is read. An upcast is declared from one event descriptor to another, and an event store wrapper applies it to everything that store returns. Handlers, states and processors receive only the current shape, and the log is never rewritten.

In the tool store, `ToolAdded` first recorded a tool id, a model and a name. Later each tool gets a category. Every `ToolAdded` already in the log lacks the category, and every new one has it. This page declares the two shapes as two versions of one event, declares the upcast from the first to the second, and wraps the event store with it.

## Event versions

An event descriptor has a `version`, a string that defaults to `"1.0"`. When a handler appends an event, the version of the descriptor is stored with the event, and every read returns it on the event message. Commands and queries also have a `version` on their descriptors, but their messages are not stored and carry no version.

The version is information for upcasts. Handlers and states are matched to events by name alone, and nothing compares the stored version with the descriptor's. An event stored as version 1.0 that reaches a handler declared for 2.0 arrives as it was stored: a field that 2.0 added is missing, and the payload is not validated against the 2.0 schema unless the handler is wrapped in `validatingHandler`. Upcasting is what brings stored events to the version the code expects.

A change that stored events already satisfy needs no upcast. Adding an optional field to a payload schema is an example: old events lack the field and the code that reads it treats it as absent. A change that old events do not satisfy, such as a new required field, a field with a different type or a different name, or an event with a new name, needs an upcast.

## Declaring the versions

Declare the outdated version as a descriptor of its own, next to the current one. It has the same name and the old version and payload schema. Both are ordinary event descriptors, and the old one is used only by the upcast.

```ts
// The shape in the log: every ToolAdded written before tools had a category.
export const ToolAddedV1 = ns.event("ToolAdded", {
  version: "1.0",
  payload: z.object({ toolId: z.string(), model: z.string(), name: z.string() }),
  tags: { toolId: (payload) => payload.toolId },
})

// The shape the code uses today.
export const ToolAdded = ns.event("ToolAdded", {
  version: "2.0",
  payload: z.object({ toolId: z.string(), model: z.string(), name: z.string(), category: z.string() }),
  tags: { toolId: (payload) => payload.toolId },
})
```

The current descriptor is the one that handlers, states and `ctx.append` use from now on. New events are stored as version 2.0.

## Declaring an upcast

`upcast(from, to, map)` declares one step from the descriptor `from` to the descriptor `to`. `map` receives the stored payload, typed by the schema of `from`, and the stored event as its second argument, for its metadata and timestamp. It returns the payload of `to`, typed by the schema of `to`. The store sets the name and the version of the event from `to`.

```ts
export const addCategory = upcast(ToolAddedV1, ToolAdded, (payload) => ({ ...payload, category: "uncategorized" }))
```

The payload is typed as the 1.0 shape, so a misspelt field is a compile error, and the result has to be the 2.0 shape. An upcast returns exactly one event for each event it is applied to: it cannot drop an event or turn one into several. An event that no upcast is declared from is handed back as it is.

An upcast cannot change what an event is found by. Tags were written when the event was appended, and the reads that found it were matched against them. A field that is added to a payload cannot become a tag for events that were stored without it.

### Several versions

List one upcast per step, from 1.0 to 2.0 and from 2.0 to 3.0. An event goes through every step that applies to it, whatever order the steps are listed in, so an event stored as 1.0 is handed out as 3.0. Here `ToolAddedV2` is the 2.0 descriptor and `ToolAdded` is the 3.0 one.

```ts
// One upcast per step. An event goes through every step that applies to it.
const toV2 = upcast(ToolAddedV1, ToolAddedV2, (payload) => ({ ...payload, category: "uncategorized" }))
const toV3 = upcast(ToolAddedV2, ToolAdded, (payload) => payload)
```

There is at most one upcast from a descriptor. Two upcasts from the same descriptor, or steps that lead back to the descriptor they started from, make `upcastingEventStore` throw when the store is built.

## Wrapping the event store

`upcastingEventStore(store, upcasts)` takes the list of upcasts and returns a store of the same type as the one it wraps, with every read passed through them. You wrap the store where the application is assembled, and handlers, states and processors use the wrapped store.

```ts
const log = inMemoryEventStore()
const eventStore = upcastingEventStore(log, [addCategory])
```

Reads by states and by processors both go through the upcasts. Appends go to the wrapped store as they are, and a snapshotting or scheduling store inside the wrapper keeps working.

### What is stored

Nothing about the stored events changes. The event is in the log as version 1.0 for as long as the log exists, and every read converts it again. Changing an upcast takes effect on the next read of every event, with nothing to migrate. Keep `map` a pure function of the event, with no I/O and no clock, because it runs on every read of an old event.

A handler wrapped in `validatingHandler` checks its payload against the current schema, and it receives the event after the upcast, so a 1.0 event is validated in its 2.0 form. [Interception and validation](/docs/kronos-ts/interception-and-validation) covers `validatingHandler`.

## Renaming an event

An upcast whose two descriptors have different names renames the event. The log keeps the name that each event was written under, and the code uses the current name. Declare the stored name as a descriptor and the upcast from it to the current one, and no other declaration is needed.

```ts
// What the log holds from before the event was renamed.
export const RentalOverdue = ns.event("RentalOverdue", {
  version: "1.0",
  payload: z.object({ toolId: z.string(), customerId: z.string() }),
  tags: { toolId: (payload) => payload.toolId, customerId: (payload) => payload.customerId },
})
```

```ts
export const lapsedRentals = upcast(RentalOverdue, RentalLapsed, (payload) => payload)
```

The example renames `RentalOverdue` to `RentalLapsed`. Where a read, a processor's stream or an append condition names `RentalLapsed`, the store reads the log for `RentalOverdue` as well. A processor that handles `RentalLapsed` receives the events stored as `RentalOverdue`, converted. A state that folds `RentalLapsed` reads them too, and an append conditioned on `RentalLapsed` conflicts with an event appended under the old name.

A read whose query has several items is refused with an error when one stored name is upcast to types that items with different tags select. Read those items with separate queries.

## Snapshots and read models

A snapshot holds a state folded before the change, and the upcast does not convert it. If the upcast changes what an old event means to a state, change that snapshot's key, as described on [Snapshots](/docs/kronos-ts/snapshots).

A read model that an event handler built before the change keeps what the handler wrote then. To rebuild it from the converted events, reset the processor and replay it, as described on [Event processors](/docs/kronos-ts/event-processors).

## Errors

An upcast that throws fails the read that reached the event: the command that loaded a state fails, and a processor handles it as any handler failure. An event with no upcast declared from its descriptor and the wrong shape for the code reaches the handler as stored, and nothing reports it unless the handler is wrapped in `validatingHandler`. `upcastingEventStore` throws when two upcasts are declared from one descriptor or when steps lead back to their start, and a read with several items is refused with an error when it cannot determine which item an upcast event was read for.
