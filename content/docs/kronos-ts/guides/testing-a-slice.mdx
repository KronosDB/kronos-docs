When you are done, the renting slice has one test per scenario: a rental, each of its three refusals, and a command sent twice. The inventory has a storyline that follows a tool from added to rented. Every test runs the slice through the same wrappers as `main.ts`, from [Organize an app into slices](/docs/kronos-ts/guides/slices), so a test exercises the same wrappers as production. You need that layout, a test runner, and `@kronos-ts/test`. The tests use Bun's runner, `bun:test`; on Node.js the same tests run with `node:test`, as described under [On Node.js](#on-nodejs).

## Build the app for a test

A test composes the slices it tests exactly as `main.ts` composes every slice, over test infrastructure: the log in memory, wrapped in `recordingEventStore`, and the command bus wrapped in `recordingCommandBus`, which is how the fixture observes what the app did. `test.ts` beside `main.ts` holds the function every test file calls:

```ts
const eventStore = recordingEventStore(inMemoryEventStore())
const commandBus = recordingCommandBus(localCommandBus(unitOfWork))
const queryBus = localQueryBus(unitOfWork)
```

`testInfrastructure()` returns three functions. `app(handlers)` takes one set of the three lists, a slice's or a context's, and passes them to `kronos()` with the same wrappers and infrastructure as `main.ts`, and stops the app after the file's last test. `eventProcessor` is the function a read model slice takes, applied to the test's stores:

```ts
eventProcessor: (name: string) =>
  database
    ? eventProcessor(name, eventStore, postgresTokenStore(pg), postgresUnitOfWork(unitOfWork, pg))
    : eventProcessor(name, eventStore, inMemoryTokenStore(), unitOfWork),
```

`deadLettering` is the function a slice whose processor parks failures takes, applied to a dead-letter queue of the test's own, in the test's database or in memory:

```ts
deadLettering: (processor: EventProcessor, sequence: Sequence) => deadLettering(processor, deadLetterQueue, sequence),
```

A command slice needs no database. `testInfrastructure({ db: true })` creates a database for the test file, runs the migrations in it, drops it after the last test, and puts the processors' positions in it. Without it, the app is given a pool that is never opened, which a slice without tables never uses. Set `TEST_DATABASE_URL` to a server where the tests may create databases.

## One fixture per file

The test file sits in the slice's folder and builds one fixture, over an app with only the slice it tests:

```ts
const { app } = await testInfrastructure()
const scenarios = fixture(app(rentTool()))
```

The scenarios in a file share the app, and nothing is reset between them. Each scenario therefore uses ids of its own, so the events one scenario appends never reach the state another loads. Small functions return the facts with a new id each time:

```ts
const drill = () => ({ toolId: crypto.randomUUID(), model: "DCD791", name: "Cordless drill" })
const customer = (maxRentals: number) => ({ customerId: crypto.randomUUID(), name: "Ada", maxRentals })
```

## Write one test per scenario

Each test is one scenario of the slice, named for what it shows. `given` lists the events already in the log, `when` sends the command, and `then` claims the result and the appended events:

```ts
it("rents an available tool to a registered customer", async () => {
  const [tool, ada] = [drill(), customer(1)]
  const rental = { toolId: tool.toolId, customerId: ada.customerId }
  await scenarios
    .given(event(ToolAdded, tool), event(CustomerRegistered, ada))
    .when(command(RentTool, rental))
    .then(result({ ok: true }), events(event(ToolRented, rental)))
})
```

A refusal is a command result, so its test claims it with `result(...)`, with the rejection's facts. It also claims `noEvents()`, because a refused rental records nothing:

```ts
it("refuses a customer at their limit", async () => {
  const [first, second, ada] = [drill(), drill(), customer(1)]
  await scenarios
    .given(event(ToolAdded, first), event(ToolAdded, second), event(CustomerRegistered, ada))
    .given(event(ToolRented, { toolId: first.toolId, customerId: ada.customerId }))
    .when(command(RentTool, { toolId: second.toolId, customerId: ada.customerId }))
    .then(result({ ok: false, rejection: "OVER_LIMIT", customerId: ada.customerId, maxRentals: 1 }), noEvents())
})
```

`given` can be called more than once. The calls accumulate in order, and every event is appended and handled before the command is sent. The scenarios for `TOOL_UNAVAILABLE` and `CUSTOMER_UNKNOWN` follow the same shape.

Test what the slice decides, not what the wrappers in `main.ts` do. Validation, correlation and the database are the same for every slice, and are tested once for the whole application.

A command sent again after it succeeded is a scenario of its own. The rental is already in the log, so the result is `{ ok: true }` and nothing is appended:

```ts
.given(event(ToolAdded, tool), event(CustomerRegistered, ada), event(ToolRented, rental))
.when(command(RentTool, rental))
.then(result({ ok: true }), noEvents())
```

## Test the read model with a storyline

A read model is tested through its query. The inventory's test file requests a database, because the projection writes the `inventory` table, and passes the slice its `eventProcessor`:

```ts
const { app, eventProcessor } = await testInfrastructure({ db: true })
const scenarios = fixture(app(inventory(eventProcessor)))
```

A storyline starts from the query. Each `after` appends events and waits until the projection's processor has handled them, and each `shows` claims the query's result at that point, so the test neither sleeps nor polls:

```ts
await scenarios
  .storyline(query(GetInventory, {}))
  .shows([])
  .after(event(ToolAdded, { toolId: "t-1", model: "DCD791", name: "Cordless drill" }))
  .shows([{ toolId: "t-1", name: "Cordless drill", available: true }])
  .after(
    event(CustomerRegistered, { customerId: "ada", name: "Ada", maxRentals: 1 }),
    event(ToolRented, { toolId: "t-1", customerId: "ada" }),
  )
  .shows([{ toolId: "t-1", name: "Cordless drill", available: false }])
```

`GetInventory` returns every tool in the table, so this file holds one storyline and the ids can be the sample data. A query that returns rows for one id, such as one customer's rentals, takes the same per-scenario ids as the command tests. If a beat fails, the error names the beat and the steps before it.

## On Node.js

`@kronos-ts/test` does not depend on a test runner, so the tests run with `node:test` unchanged except for two imports. Import `it` from `node:test` instead of `bun:test` in each test file, and in `test.ts` import `after` from `node:test` where the Bun version imports `afterAll`. Run the tests through tsx, so that Node.js loads the TypeScript files:

```sh
node --import tsx --test 'src/**/*.test.ts'
```

## Checking it works

Run the slices' tests from the project directory:

```sh
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/postgres bun test src/slices
```

```text title="Output"
 6 pass
 0 fail
Ran 6 tests across 2 files.
```

To produce a failure message, change `maxRentals: 1` in the claim of the limit scenario to `2`. The output starts with the scenario as a sentence, lists the expected and the returned result, and prints `maxRentals: expected 2, got 1` under the differences.
