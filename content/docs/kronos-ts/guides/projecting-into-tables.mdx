title: Project into your own tables
description: Build the inventory slice, a Postgres table that its event handlers write in the same transaction as the processor's position, and a query handler that reads it.
---

When you are done, the inventory slice keeps one row per tool in an `inventory` table. Its event handlers write the table with SQL, its query handler reads it, and every write commits together with the processor's position, so the table always matches the events the processor has handled. You need the slice layout from [Organize an app into slices](/docs/kronos-ts/guides/slices) and the Postgres setup from [Run on Postgres](/docs/kronos-ts/guides/running-on-postgres).

This guide writes the table with plain SQL through `ctx.sql()`. [Use Drizzle for typed tables](/docs/kronos-ts/guides/drizzle) puts a Drizzle client on the same transaction. We recommend it: the compiler checks every column and value against the table's schema, the handlers contain typed calls instead of SQL strings, and each call still sends one statement on the same connection.

## Create the table

The table belongs to the slice, so the statement that creates it is in the slice's `table.ts`:

```ts
export const createInventoryTable = `
  CREATE TABLE IF NOT EXISTS inventory (
    tool_id   text PRIMARY KEY,
    name      text NOT NULL,
    available boolean NOT NULL
  )`
```

`migrations.ts` lists the statements of every slice in the order they were added, and `main.ts` runs them after `pg.start()`. If a migration tool owns your database, give it the same statements instead.

```ts
const migrations = [createInventoryTable]

export async function migrate(pg: PostgresResource): Promise<void> {
  for (const statement of migrations) await pg.query(statement)
}
```

## Write the table from event handlers

An event handler reaches the database through `ctx.sql()`, and declares it in its context's type as `ctx: EventHandlerContext & PostgresCapability`. In an event handler, `ctx.sql()` returns the transaction of the batch being delivered, so every statement commits or rolls back with the processor's position.

`projection.ts` holds the slice's two event handlers. `ToolAdded` inserts the row and `ToolRented` marks the tool as out:

```ts
export const projection = [
  eventHandler(ToolAdded, async ({ payload }, ctx: EventHandlerContext & PostgresCapability) => {
    await ctx.sql().query(
      `INSERT INTO inventory (tool_id, name, available) VALUES ($1, $2, true)
       ON CONFLICT (tool_id) DO UPDATE SET name = EXCLUDED.name`,
      [payload.toolId, payload.name],
    )
  }),
  eventHandler(ToolRented, async ({ payload }, ctx: EventHandlerContext & PostgresCapability) => {
    await ctx.sql().query(`UPDATE inventory SET available = false WHERE tool_id = $1`, [payload.toolId])
  }),
]
```

The insert is an upsert and the update sets a value instead of toggling one, so handling an event twice leaves the same row, as described under [Idempotency](#idempotency).

## Read it from a query handler

The query handler reads the same table. In a query handler, `ctx.sql()` is the pool, so the read returns what the processor has committed.

```ts
export const handle = queryHandler(GetInventory, async (_query, ctx: QueryHandlerContext & PostgresCapability) => {
  const rows = await ctx.sql().query<{ tool_id: string; name: string; available: boolean }>(
    `SELECT tool_id, name, available FROM inventory ORDER BY tool_id`,
  )
  return rows.map((row) => ({ toolId: row.tool_id, name: row.name, available: row.available }))
})
```

## Name the processor

The slice's `index.ts` declares its processor, beside the handlers it delivers to, and names it for the table it writes. It receives `eventProcessor`, Kronos's `eventProcessor` with the stores already applied, so it gives only the name and the batch size:

```ts
export const inventory = (eventProcessor: (name: string) => EventProcessor) => {
  // Named for the table it writes. A batch of up to 100 events commits in one transaction with the position.
  const processor = batched(eventProcessor("inventory-view"), 100)
```

The name is where the processor's position is stored. When a change to the handlers means the table has to be rebuilt, either give the processor a new name, so it starts from the beginning of the log, or reset it as in [Replay a projection](/docs/kronos-ts/guides/replaying-a-projection).

`main.ts` wraps every query and event handler in `postgresHandler`, which supplies `ctx.sql()`, over the same pool that `main.ts` builds the processor's token store and unit of work from:

```ts
handler: pipe(
  handler.handler,
  (next) => postgresHandler(next, pg),
  (next) => validatingHandler(next, handler.descriptor),
),
```

A handler given a different pool, or an SQL client of your own, writes outside the batch's transaction. [Postgres](/docs/kronos-ts/infrastructure/postgres) describes how to give the transaction to a query builder.

## Why the table and the position commit together

A processor writes its new position in the same transaction as the handlers' writes. If a handler throws, both roll back and the processor retries the batch. After a restart the processor resumes at the stored position, and the table reflects exactly the events before it, as [Event processors](/docs/kronos-ts/event-processors) describes.

## Idempotency

A handler is idempotent when handling an event twice leaves the same rows as handling it once. Both inventory handlers are: the insert is an upsert on the tool id and the update assigns a value. A replay that does not clear the table therefore leaves the existing rows as they were.

In a command handler `ctx.sql()` is the pool, not a transaction. Its writes commit as they run, before the events are appended, and a rejected append does not undo them. A retried command runs them again, so write them as upserts keyed by an id the command carries.

## Write only this projection's tables

A projection writes only its own tables, and calls nothing outside the system. A replay runs its handlers again from the start of the log, so they must write the same rows every time, and a call to another system would repeat with every replay and could return something different. [Write an automation](/docs/kronos-ts/guides/automations) builds the alternative: what another system reports comes into the log as an event, through an automation, and the projection reads that event.

A projection's tables also belong to it alone: another slice reads them through the projection's query, not with SQL of its own.

## Make replays faster

The handlers above send one statement per event. That is right at the head of the log, where a batch holds one or two events. While the processor catches up or replays, it sends one round trip per event, and a projection with many events to replay is faster when it writes once per batch. [Speed up a projection](/docs/kronos-ts/guides/optimizing-projections) measures the options and builds each one for this inventory.

## Checking it works

Run `main.ts` against a database. It adds two tools, registers two customers, sends four rentals of which one succeeds, waits until the projection has caught up and prints the query result:

```sh
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/toolstore bun run main.ts
```

```text title="Output"
ada rents t-1: rented
grace rents t-1: TOOL_UNAVAILABLE
ada rents t-2: OVER_LIMIT
linus rents t-2: CUSTOMER_UNKNOWN
t-1  Cordless drill  rented
t-2  Tile saw        available
```

The table holds the same two rows:

```sh
psql "$DATABASE_URL" -c 'select * from inventory'
```

```text title="Output"
 tool_id |      name      | available
---------+----------------+-----------
 t-2     | Tile saw       | t
 t-1     | Cordless drill | f
(2 rows)
```

The processor's position is in the same database:

```sh
psql "$DATABASE_URL" -c 'select processor_name, token from kronos_token_entries'
```

```text title="Output"
 processor_name |              token
----------------+---------------------------------
 inventory-view | {"position":"5","gapKey":"763"}
(1 row)
```
