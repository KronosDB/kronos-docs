---
title: Run on Postgres
description: Build the tool store's event store, processors and read models over one Postgres pool, so that they share its transactions.
---

When you are done, `main.ts` builds everything the tool store stores from one Postgres pool: the event log, the processors' positions and the read models. Each command and each batch of events commits in a Postgres transaction. You need a Postgres 14 or later database you can create tables in, and the slice layout from [Organize an app into slices](/docs/kronos-ts/guides/slices), where `main.ts` composes the slice functions.

The slices do not change in this guide. Only `main.ts` opens Postgres, and the tests keep their event log in memory through `testInfrastructure`, as described in [Test a slice](/docs/kronos-ts/guides/testing-a-slice).

## Install the package

`@kronos-ts/postgres` connects to the database through a driver you choose. A connection string loads `pg` (node-postgres), so install both:

<Tabs groupId="runtime" persist items={["Bun", "Node.js"]}>
<Tab value="Bun">

```sh
bun add @kronos-ts/postgres pg
```

</Tab>
<Tab value="Node.js">

```sh
npm install @kronos-ts/postgres pg
```

</Tab>
</Tabs>

For another driver, install `postgres` (porsager) or use Bun's built-in `Bun.sql`, and pass the adapter to the pool as shown under [Connect a pool](#connect-a-pool). The [Postgres page](/docs/kronos-ts/infrastructure/postgres) lists the adapters.

If you have no database to hand, this starts one on port 5432:

```sh
docker run -d --name toolstore-pg -p 5432:5432 \
  -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=toolstore postgres:17
```

## Connect a pool

`postgresPool` takes a connection string, and `start()` connects it and creates the Kronos tables if they are missing. Every resource in this guide is built from this one pool, so `main.ts` builds it first and runs the slices' migrations after it:

```ts
const pg = postgresPool(process.env.DATABASE_URL ?? "postgresql://postgres:postgres@localhost:5432/toolstore")
await pg.start()
await migrate(pg)
```

A pool that is built from a connection string cannot be used before `start()` resolves. To set the pool size or the per-transaction timeouts, build the adapter yourself and pass it to the pool:

```ts
export const pooled = postgresPool(pgAdapter({ connectionString, poolConfig: { max: 20 } }))
```

## Create the schema

With the default options, `pg.start()` creates five tables if they are missing:

| Table | Holds |
| --- | --- |
| `kronos_events` | The event log. |
| `kronos_token_entries` | One row per processor segment: its position and its claim. |
| `kronos_snapshots` | Cached state folds, used by the snapshotting store. |
| `kronos_scheduled_events` | Events scheduled for a later time. |
| `kronos_dead_letters` | Events that a dead-lettering processor parked. |

The read model tables are the slices' own. `migrate(pg)` runs the statements each slice declares, such as the inventory's `createInventoryTable`, as described in [Project into your own tables](/docs/kronos-ts/guides/projecting-into-tables#create-the-table).

If a migration tool owns the database, start the pool with `bootstrap: false` and give the tool the same statements. The package exports one DDL builder per table (`buildEventsTableDDL` and the others) that returns the statement:

```ts
export const migrated = postgresPool(connectionString, { bootstrap: false })
```

Table names are an option of the pool (`tableNames`), because every store built from the pool reads and writes the same tables.

## Build the infrastructure

`postgresUnitOfWork(unitOfWork, pg)` gives every command and every batch of events a Postgres transaction, which the event store, the token store and the handlers' `ctx.sql()` join. The command bus takes it. The query bus keeps the plain `unitOfWork`, because a query only reads and `localQueryBus` rejects a transactional factory:

```ts
const eventStore = postgresEventStore(pg)
const commandBus = localCommandBus(postgresUnitOfWork(unitOfWork, pg))
const queryBus = localQueryBus(unitOfWork)
```

`main.ts` then calls `handlers` from `slices/index.ts` once. The processors are built by the function the slices receive as `eventProcessor`, which applies Kronos's `eventProcessor` to the event store, a Postgres token store and the Postgres unit of work:

```ts
const app = handlers((name) =>
  eventProcessor(name, eventStore, postgresTokenStore(pg), postgresUnitOfWork(unitOfWork, pg)),
)
```

`main.ts` wraps every query and event handler with `postgresHandler(next, pg)` over the same pool, as described in [Organize an app into slices](/docs/kronos-ts/guides/slices#compose-in-maints), so a batch's table writes and its new position commit in one transaction. A token store or an SQL client built from a different pool opens a second connection, and its writes are not atomic with the rest.

## Shut down in order

Stop the app before closing the pool. `stop()` stops every processor, which writes its position, and waits for the handlers that are running, so close the pool once it resolves:

```ts
await running.stop()
await pg.close()
```

## Checking it works

Run `main.ts` with the connection string of your database:

```sh
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/toolstore bun run main.ts
```

```text title="Output"
ada rents t-1: rented
grace rents t-1: TOOL_UNAVAILABLE
ada rents t-2: OVER_LIMIT
linus rents t-2: CUSTOMER_UNKNOWN
t-1  Cordless drill  rented
t-2  Tile saw        available
```

The database holds the Kronos tables, the `inventory` table and the five events:

```sh
psql "$DATABASE_URL" -c 'select sequence_position, type from kronos_events'
```

```text title="Output"
 sequence_position |             type
-------------------+------------------------------
                 1 | toolstore.ToolAdded
                 2 | toolstore.ToolAdded
                 3 | toolstore.CustomerRegistered
                 4 | toolstore.CustomerRegistered
                 5 | toolstore.ToolRented
(5 rows)
```

Run `main.ts` a second time and the log still holds five events. Each command finds its change already in the log, returns `{ ok: true }` and appends nothing, and the processor resumes from its stored position.
