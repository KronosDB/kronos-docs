title: Replay a projection
description: Rebuild the inventory table from the start of the event log with one function in the inventory slice, and start it from an admin endpoint.
---

When you are done, the inventory slice has a `replayInventory` function that rebuilds its table from the first event in the log, and an admin endpoint starts it and reports its progress. You need the inventory slice from [Project into your own tables](/docs/kronos-ts/guides/projecting-into-tables): a processor named `inventory-view` whose event handlers write the `inventory` table through `ctx.sql()`.

Replay a projection after you change what its handlers write, add a column, or fix a bug in them. The log is not changed. The processor reads it again from the start, and the handlers write the table anew.

## Write the replay in the slice

The replay belongs to the slice, because the slice declares both the processor and the table it writes. `replay.ts` in the `inventory` folder stops the processor, rewinds it to the start of the log while emptying the table, and starts it again:

```ts
export async function replayInventory(processor: RunningProcessor): Promise<void> {
  await processor.stop()
  await processor.resetTokens(0n, async (uow) => {
    const tx = await postgresTransaction(uow)
    await tx.query(`TRUNCATE inventory`)
  })
  await processor.start()
}
```

`resetTokens(startPosition, reset)` moves the stored position to `startPosition`, where `0n` is the start of the log. The `reset` function runs in the transaction that stores the new position, and `postgresTransaction(uow)` returns that transaction. The truncate and the new position therefore commit together. If either fails, the old rows and the old position both stay.

Without the truncate, the replay would write over the old rows, and a row that no handler produces any more would stay in the table. With it, the table is empty from the moment the reset commits and fills as the processor reads the log, so a query during the replay returns a partial inventory.

## Stop every node first

`resetTokens` throws if the processor is still running, and fails with an error naming the segment when another node holds one. [Event processors](/docs/kronos-ts/event-processors#reset-and-replay) describes segments and the reset. When the app runs on several nodes, stop the processor on all of them before the reset, and start it on all of them afterwards.

## Keep side effects out of the projection

A replay delivers events the handlers have already handled once. The inventory's handlers only write their table, so handling an event again is safe. Work that must not happen twice, such as sending a receipt, belongs in an automation slice with a processor of its own: replaying `inventory-view` does not touch that processor, so nothing is sent again.

A handler that must handle replayed events differently reads `ctx.isReplay()`, which is `true` for events up to the position the processor had reached when it was reset, and `false` after that.

## Start it from an admin endpoint

The admin endpoint lists the processors that can be replayed, each with its replay function. A processor that is not in the list cannot be reset from the endpoint, because the endpoint has no function that clears its table:

```ts
const replays: Record<string, (processor: RunningProcessor) => Promise<void>> = {
  "inventory-view": replayInventory,
}
```

`admin(processors)` returns two functions, one per route, from a processor name to a `Response`. It takes `app.processors`, the running processors keyed by name:

```ts
async replay(name: string): Promise<Response> {
  const processor = processors.get(name)
  const replay = replays[name]
  if (processor === undefined || replay === undefined) {
    return Response.json({ error: `${name} cannot be replayed` }, { status: 404 })
  }
  try {
    await replay(processor)
  } catch (error) {
    return Response.json({ error: String(error) }, { status: 409 })
  }
  return Response.json({ replaying: processor.replaying }, { status: 202 })
},
```

A failed reset returns 409 and leaves the table and the position as they were. The endpoint returns 202 once the processor has started again, not when the replay has finished. `status` returns `processor.status()`: whether the processor is running, its position as a string, whether it has caught up with the log, and whether it is replaying. A client polls it until `replaying` is `false`.

Mount the two functions on your server's routes. With `Bun.serve`:

```ts
routes: {
  "/admin/processors/:name": { GET: (request) => routes.status(request.params.name) },
  "/admin/processors/:name/replay": { POST: (request) => routes.replay(request.params.name) },
},
```

Put the routes behind your own authentication, because a replay deletes the table's rows.

## Checking it works

`check.ts` builds the app over Postgres, adds two tools, rents one, then calls the replay route over HTTP, polls the status until the replay has finished, and prints the inventory again. To check that the table is rebuilt from the log, first insert a row that no event produced:

```sh
psql "$DATABASE_URL" -c "insert into inventory values ('junk', 'junk', true)"
bun run check.ts
```

```text title="Output"
before replay: junk available, t-1 rented, t-2 available
POST replay 202 {"replaying":true}
GET status {"running":true,"position":"4","caughtUp":true,"replaying":false}
after replay: t-1 rented, t-2 available
```

The replay removed the `junk` row, because no event in the log produces it.
