description: Start a KronosDB server, declare a context for the tool store, and build the app's event store and buses over it while the read models stay in Postgres.
---

When you are done, a KronosDB server holds the tool store's events in a context named `toolstore`, and the app's commands and queries go through that server, so they reach every instance of the app. The read models and the processors' positions stay in Postgres. You need Docker to run the server, and the tool store from [Run on Postgres](/docs/kronos-ts/guides/running-on-postgres). KronosDB 0.12 or later is required, because the client uses KronosDB's native protocol.

The slices do not change. `main.ts` builds three things over KronosDB instead of Postgres: the event store, the command bus and the query bus.

## Start the server

KronosDB listens on two ports. Port 50051 serves everything a Kronos application sends: events, commands and queries. Port 9240 is HTTP, for the admin console, health probes, the admin API and Prometheus metrics. The image keeps its data in the volume `/data`.

```sh
docker run -d --name kronosdb -p 50051:50051 -p 9240:9240 \
  -v kronosdb-data:/data \
  ghcr.io/kronosdb/kronosdb:0.17.0
```

The server is ready when `/ready` on the admin port returns 200:

```sh
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:9240/ready
```

This server accepts every connection and logs a warning that authentication is disabled. That is acceptable on your own machine. [Security](/docs/kronosdb/security) describes the tokens and TLS settings to apply before the port is reachable from anywhere else.

## Declare a context

A **context** is one event log, and a KronosDB server holds as many as you declare. The server creates one called `default`; the tool store uses its own, so that its events are separate from other applications on the same server. The server reads the contexts to create from a manifest file, which is a TOML file with one table per context.

```toml title="kronosdb-manifest.toml"
[[contexts]]
name = "toolstore"
```

Mount the file into the container and point `KRONOSDB_MANIFEST` at it. The server creates missing contexts at startup and watches the file while it runs. It never deletes a context that you remove from the file.

```sh
docker run -d --name kronosdb -p 50051:50051 -p 9240:9240 \
  -v kronosdb-data:/data \
  -v "$PWD/kronosdb-manifest.toml:/etc/kronosdb/manifest.toml:ro" \
  -e KRONOSDB_MANIFEST=/etc/kronosdb/manifest.toml \
  ghcr.io/kronosdb/kronosdb:0.17.0
```

A context can also be created from the admin console. [Contexts](/docs/kronosdb/contexts) describes what a context holds and [Configuration](/docs/kronosdb/configuration) lists the server's settings and environment variables.

## Connect

`kronosDbConnection` takes the address of the server, the `context` to use by default, a `componentName` that identifies this application to the server, and the serializer for event and message payloads. The event store and both buses share the one connection.

```ts
const kdb = await kronosDbConnection({
  host: process.env.KRONOSDB_HOST ?? "localhost",
  port: Number(process.env.KRONOSDB_PORT ?? 50051),
  context: "toolstore",
  componentName: "toolstore",
  serializer: jsonSerializer(),
})
```

When the server requires a token or TLS, the same options object takes `token` and `ssl`. [KronosDB](/docs/kronos-ts/infrastructure/kronosdb) lists every option.

## Build the event store and the buses

The event store takes the connection and the name of the context. Each bus wraps a local bus, which runs the handlers of this instance, and takes the connection and the name of a bus. A **bus** in KronosDB is a namespace for commands and queries, independent of contexts, and the tool store gives its buses the same name as its context.

```ts
const eventStore = kronosDbEventStore(kdb, "toolstore")
const commandBus = kronosDbCommandBus(localCommandBus(unitOfWork), kdb, "toolstore")
const localQueries = localQueryBus(unitOfWork)
const queryBus = localFirstQueryBus(kronosDbQueryBus(localQueries, kdb, "toolstore"), localQueries)
```

[Split across processes](/docs/kronos-ts/guides/across-processes) describes local-first buses. Every command is sent to the server, even when this instance handles it. The server spreads commands over the instances that handle them, so with several instances each takes a share. Queries are handled locally first with `localFirstQueryBus`: every instance reads the same Postgres tables, so another instance would return the same rows after a round trip.

## Compose the app

The event store and the buses come from KronosDB. The processors' token store and unit of work come from Postgres as before, so a batch's table writes and its new position still commit in one Postgres transaction. Only what `main.ts` opens changes; the slices and the context do not:

```ts
const handlers = [
  ...toolstore((name) => eventProcessor(name, eventStore, postgresTokenStore(pg), postgresUnitOfWork(unitOfWork, pg))),
]
```

The handlers are then passed to `kronos()` with the same wrappers as in [Organize an app into slices](/docs/kronos-ts/guides/slices#compose-in-maints), and the connection is started:

```ts
await kdb.start()
```

The command bus takes the plain `unitOfWork`, because a command's events are appended to KronosDB, not written in a Postgres transaction. Await `kdb.start()` after `kronos()`. It resolves once the server has acknowledged every handler, and from then on the server can route commands and queries to them.

At shutdown, stop the app first, so that the processors and the running handlers finish. Then close the connection, which drains the buses and closes the socket, and close the pool last:

```ts
await app.stop()
await kdb.close()
await pg.close()
```

Remote administration is separate and optional. With `kronosDbControlPlane(kdb, toolstore.processors)`, created before `kdb.start()`, the admin console can pause, start, split and merge this application's processors and shows their status.

## Checking it works

Run `main.ts` against the server and the database:

```sh
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/toolstore bun run main.ts
```

```text title="Output"
ada rents t-1: rented
grace rents t-1: TOOL_UNAVAILABLE
ada rents t-2: OVER_LIMIT
linus rents t-2: CUSTOMER_UNKNOWN
t-1  Cordless drill  rented
t-2  Tile saw        available
```

The server's admin API reports how many events the `toolstore` context holds:

```sh
curl -s http://localhost:9240/api/v1/contexts | jq -c '.[] | select(.name == "toolstore") | {name, head}'
```

```text title="Output"
{"name":"toolstore","head":5}
```

If the context name is not one the server has, the processor logs a stream error that reads `context not found` followed by the name. Declare the context in the manifest and restart the application.
