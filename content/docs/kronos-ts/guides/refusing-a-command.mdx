---
title: Refuse a command
description: Declare each refusal of a command with its code and facts, return it from the handler, accept a command sent twice, and turn every outcome into a reply.
---

When you are done, `RentTool` declares each business refusal with a code and the facts the caller may read, the handler returns a refusal without appending, a rental sent twice succeeds once, and an HTTP caller turns each outcome into a reply. You need the renting slice from [Organize an app into slices](/docs/kronos-ts/guides/slices), or any command handler that can refuse.

## Choose result or error

A command has three kinds of outcome. A **rejection** is a business rule that refused the command: the tool is out, the customer is not registered, the customer is at their limit. The caller reads it and acts on it, so the handler returns it as the command's result and appends nothing.

A command that has already succeeded, sent again, is not refused. Its handler finds the change already in the log, returns `{ ok: true }` and appends nothing, so a caller that timed out can send the same command again.

Everything else is an error, thrown: a bug, a broken invariant, an append whose condition failed, or a store that cannot be reached. The caller can only send the command again or report the error. Throwing rolls the command back, and nothing is appended.

## Declare the result

The command's descriptor declares every outcome in its `result` schema. Success is `{ ok: true }`. Each rejection is `{ ok: false }` with a `rejection` code, named for the rule in upper snake case, and the facts the decision saw that the caller may read:

```ts
export const RentTool = ns.command("RentTool", {
  payload: z.object({ toolId: z.string().min(1), customerId: z.string().min(1) }),
  result: z.union([
    z.object({ ok: z.literal(true) }),
    z.object({ ok: z.literal(false), rejection: z.literal("TOOL_UNAVAILABLE"), toolId: z.string() }),
    z.object({ ok: z.literal(false), rejection: z.literal("CUSTOMER_UNKNOWN"), customerId: z.string() }),
    z.object({
      ok: z.literal(false),
      rejection: z.literal("OVER_LIMIT"),
      customerId: z.string(),
      maxRentals: z.number().int(),
    }),
  ]),
})
```

The handler's return value is type-checked against the schema, and the caller's `send` resolves with the same type. `if (outcome.ok)` narrows it to success, and a `switch` on `outcome.rejection` narrows each case to its own facts. [Results](/docs/kronos-ts/messages#results) describes result schemas. A command that cannot be refused still declares `z.object({ ok: z.literal(true) })`, so every command returns the same shape.

## Return a rejection

The handler loads the state, checks the rules in order, and returns a rejection before it appends anything. Only the success path appends:

```ts
if (!renting.toolAdded || rentalsOfTool.length > 0) return { ok: false, rejection: "TOOL_UNAVAILABLE", toolId }
if (!renting.customer.registered) return { ok: false, rejection: "CUSTOMER_UNKNOWN", customerId }
const { maxRentals } = renting.customer
if (rentalsOfCustomer.length >= maxRentals) return { ok: false, rejection: "OVER_LIMIT", customerId, maxRentals }

ctx.append(ToolRented, payload)
return { ok: true }
```

The order of the checks decides which rejection is returned when several rules apply. The handler returns plain object literals; the result schema gives them their type.

## Accept a command sent twice

Before the rules, the handler checks whether what the command would record is already true. A customer who already has this tool has already rented it, so the handler returns success and appends nothing:

```ts
if (rentalsOfTool.some((rental) => rental.customerId === customerId)) return { ok: true }
```

Without this check, the second send would return `TOOL_UNAVAILABLE` to the customer who holds the tool. The same check makes `AddTool` and `RegisterCustomer` succeed once for a given id. This works because the command carries the ids of what it creates, chosen by the caller, so a command sent again names the same tool and customer.

## Leave errors to the caller

A handler throws only for a bug or a broken invariant, and catches nothing. Kronos throws for the rest: a failed append condition, a store or bus that cannot be reached, a command that no handler handles. Each error carries a kind that a caller tests with the guards `isConflict`, `isUnavailable` and `isNoHandler`. The guards read the error's `kind` field, so they also work on errors that crossed a transport. The commands page lists the kinds under [Failures](/docs/kronos-ts/commands#failures).

## Handle each outcome in the caller

The caller reads the result and switches on the rejection, and wraps the call to deal with errors. An HTTP endpoint returns 404 for a rejection whose rule is that something does not exist, and 409 for any other rejection. A conflict is also 409, and the client sends the command again; unavailable infrastructure is 503. Any other error is rethrown, to be reported as a server error:

```ts
export async function rentEndpoint(commandBus: CommandBus, toolId: string, customerId: string): Promise<Reply> {
  try {
    const outcome = await send(commandBus, RentTool, { toolId, customerId })
    if (outcome.ok) return { status: 200, body: { message: `${customerId} rented ${toolId}` } }

    switch (outcome.rejection) {
      case "TOOL_UNAVAILABLE":
        return { status: 409, body: { message: `${outcome.toolId} is not on the shelf` } }
      case "CUSTOMER_UNKNOWN":
        return { status: 404, body: { message: `${outcome.customerId} is not registered` } }
      case "OVER_LIMIT":
        return { status: 409, body: { message: `${outcome.customerId} is at their rental limit (${outcome.maxRentals})` } }
    }
  } catch (failure) {
    if (isConflict(failure)) return { status: 409, body: { message: "the tool or the customer changed, send it again" } }
    if (isUnavailable(failure)) return { status: 503, body: { message: "try again shortly" } }
    throw failure
  }
}
```

Each message is built from the rejection's facts. The function declares its return type, so a rejection added to the schema without a `case` here fails to compile.

## Test each outcome

The renting slice's tests in [Test a slice](/docs/kronos-ts/guides/testing-a-slice) claim each rejection with `result(...)` and `noEvents()`, and the command sent twice with `result({ ok: true })` and `noEvents()`. A thrown error is claimed with `error(...)`, described on [Testing](/docs/kronos-ts/testing#results-and-errors).

The caller is tested against an app with the renting slice. `app.commandBuses` holds the app's recorded command bus, which the test passes to the endpoint:

```ts
const { app } = await testInfrastructure()
const toolstore = app(rentTool())
const scenarios = fixture(toolstore)
const [commandBus] = toolstore.commandBuses
```

The test gives two tools and two customers, rents Ada the drill, and calls the endpoint once for each outcome:

```ts
expect(await rentEndpoint(commandBus!, "t-1", "ada")).toEqual({ status: 200, body: { message: "ada rented t-1" } })
expect(await rentEndpoint(commandBus!, "t-1", "linus")).toEqual({
  status: 409,
  body: { message: "t-1 is not on the shelf" },
})
```

The first call is the rental sent a second time, and it returns 200.

## Checking it works

Run the caller's test:

```sh
bun test src/guides/refusing-a-command
```

```text title="Output"
 1 pass
 0 fail
 4 expect() calls
Ran 1 test across 1 file.
```

Remove the `OVER_LIMIT` case from `rentEndpoint` and the typecheck fails, because the function can now end without returning a reply.
