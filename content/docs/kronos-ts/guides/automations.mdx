When you are done, the tool store has three automations. One notifies the customer of each rental, one sends a receipt for each rental, and one requests a service for a tool after every ten rentals. Each acts once, even when an event is handled again or a command is sent twice. You need the slice layout from [Organize an app into slices](/docs/kronos-ts/guides/slices).

An **automation** is an event handler that does something in response to events. It runs on a processor of its own, so it keeps its own position in the log, apart from the projections.

A **stateless** automation finds everything it needs in the event it handles, and loads nothing. The first two automations on this page are stateless.

A **stateful** automation decides from several events. It loads a state folded from them and acts only when the state calls for it, as the third automation on this page does.

An event handler can be run again for the same event: a failed batch is retried, and a reset replays the log. Each kind below is safe to run again, in its own way.

## Call another system directly

The first automation notifies the customer that the rental went through. It calls the notifications system from the event handler, with the event's identifier as the idempotency key:

```ts
export const automation = (notifications: Notifications) => [
  eventHandler(ToolRented, async ({ identifier, payload }) => {
    await notifications.send({ customerId: payload.customerId, text: `You have rented ${payload.toolId}.` }, identifier)
  }),
]
```

A handling that runs again calls the system again with the same key, so the system must ignore a second call with a key it has seen. Nothing is recorded in the log, so no other slice, view or test can find out that the customer was notified. Use this for a call whose outcome matters only to the outside system, such as a notification, to a system that accepts an idempotency key.

The automation takes the client as an argument. The slice declares what it needs from the notifications system as a type in its own folder, with only the call it makes:

```ts
export type Notifications = {
  send(notification: { customerId: string; text: string }, idempotencyKey: string): Promise<void>
}
```

## Record the call with a command

The second automation sends a receipt, and the tool store keeps a record of every receipt it sent. The automation still decides nothing: for each rental it sends a `SendReceipt` command, and the command's handler calls the receipts system and records `ReceiptSent`.

The event goes in the context's `events.ts` with the other events, tagged with both ids, because the command's state loads it by both:

```ts
export const ReceiptSent = ns.event("ReceiptSent", {
  payload: z.object({ toolId: z.string(), customerId: z.string() }),
  tags: { toolId: (payload) => payload.toolId, customerId: (payload) => payload.customerId },
})
```

The command goes in the slice's folder, `send-receipt`. It carries everything the call to the receipts system needs, so a second attempt sends exactly what the first did:

```ts
export const SendReceipt = ns.command("SendReceipt", {
  payload: z.object({ toolId: z.string().min(1), customerId: z.string().min(1) }),
  result: z.object({ ok: z.literal(true) }),
})
```

`state.ts` holds what the command decides with: whether this rental's receipt has been sent.

```ts
export const Receipt = state({
  id: { toolId: z.string(), customerId: z.string() },
  tags: (id) => ({ toolId: id.toolId, customerId: id.customerId }),
  evolve: [
    (): { sent: boolean } => ({ sent: false }),
    [ReceiptSent, () => ({ sent: true })],
  ],
})
```

The command's handler calls the system first and appends the event that records it afterwards, so a receipt is never recorded as sent before the receipts system has it. A receipt already recorded as sent returns `{ ok: true }` without calling anything:

```ts
export const handle = (receipts: Receipts) =>
  commandHandler(SendReceipt, async ({ payload }, ctx) => {
    const receipt = await ctx.load(Receipt, payload)
    if (receipt.sent) return { ok: true }
    await receipts.send(payload, `receipt-${payload.toolId}-${payload.customerId}`)
    ctx.append(ReceiptSent, payload)
    return { ok: true }
  })
```

The call can still repeat: the process can stop after the call and before the append, or the append can fail its condition and the command be sent again. Send an idempotency key made from the command's own ids, so the receipts system ignores a second call for the same rental, and take everything the call needs from the payload, never from a clock or a random value.

The automation sends the command for every rental and loads nothing:

```ts
export const automation = [
  eventHandler(ToolRented, async ({ payload }, ctx) => {
    await ctx.send(SendReceipt, payload)
  }),
]
```

When the event is handled again, the command is sent again and its handler finds the receipt sent. Use a command when the tool store needs a record that the call was made, or when the outside system cannot ignore a repeated call.

## Decide from several events

The third automation requests a service for a tool after every ten rentals. No single `ToolRented` shows that a tool is due, so the automation keeps a state of its own. `Wear` counts the tool's rentals since its last service was requested:

```ts
export const Wear = state({
  id: { toolId: z.string() },
  tags: (id) => ({ toolId: id.toolId }),
  evolve: [
    (): { rentalsSinceService: number } => ({ rentalsSinceService: 0 }),
    [ToolRented, (wear) => ({ rentalsSinceService: wear.rentalsSinceService + 1 })],
    [ServiceRequested, () => ({ rentalsSinceService: 0 })],
  ],
})
```

The automation loads the tool's `Wear` for each rental and sends `RequestService` when the count reaches ten:

```ts
export const automation = [
  eventHandler(ToolRented, async ({ payload }, ctx) => {
    const wear = await ctx.load(Wear, { toolId: payload.toolId })
    if (wear.rentalsSinceService < RENTALS_BETWEEN_SERVICES) return
    await ctx.send(RequestService, { toolId: payload.toolId })
  }),
]
```

The command's handler decides with the same state. It records `ServiceRequested`, which sets the count back to zero, so a command sent again for the same tool appends nothing:

```ts
export const handle = commandHandler(RequestService, async ({ payload }, ctx) => {
  const wear = await ctx.load(Wear, payload)
  if (wear.rentalsSinceService < RENTALS_BETWEEN_SERVICES) return { ok: true }
  ctx.append(ServiceRequested, payload)
  return { ok: true }
})
```

The automation and the command share the state because the event that closes the work, `ServiceRequested`, is one of the facts the decision is folded from. A state is loaded by reading every event its tags match, here every rental of one tool. When a state would read more events with every load without bound, such as every rental in the store, keep the automation's list of work in a table of the slice's own instead, written as in [Project into your own tables](/docs/kronos-ts/guides/projecting-into-tables).

## Give each automation its processor

Each slice's `index.ts` takes what its automation uses, declares the processor and returns its handlers. A processor is named for what it does. Renaming it would start it from the beginning of the log, and send a receipt for every rental again. The receipts slice takes the client, `eventProcessor` and `deadLettering`:

```ts
export const sendReceipt = (
  receipts: Receipts,
  eventProcessor: (name: string) => EventProcessor,
  deadLettering: (processor: EventProcessor, sequence: Sequence) => EventProcessor,
) => {
  // Named for what it does. A new name would send a receipt for every rental in the log again.
  const processor = deadLettering(concurrent(batched(eventProcessor("send-receipt"), 100), byCustomer), byCustomer)
  return {
```

`concurrent` sends the receipts of different customers side by side and keeps each customer's rentals in order, as described under [Sequences](/docs/kronos-ts/event-processors#sequences). `deadLettering` parks a rental whose receipt keeps failing, so it holds up only that customer's later rentals instead of the whole processor, as described under [Dead letters](/docs/kronos-ts/event-processors#dead-letters). It is given the same sequence function as `concurrent`. The notifications slice builds its processor the same way.

Like `eventProcessor`, the `deadLettering` the slice receives is Kronos's `deadLettering` with part of it applied in `main.ts`: the dead-letter queue, which belongs to the whole application. The slice gives it only what is its own, the processor and its sequences, and never receives the queue.

The service slice calls no outside system, so a failure there is a fault to fix rather than one to park. It runs the tools side by side without `deadLettering`, and takes only `eventProcessor`:


## Wire the clients in the context

The context builds each client once and passes it to every slice that uses it. Until real systems are chosen, clients that send nothing keep the application running:

```ts
const notifications: Notifications = { send: async () => {} }
const receipts: Receipts = { send: async () => {} }
```

The context takes `deadLettering` beside `eventProcessor` and passes them on, and each automation is one more line in its list:

```ts
confirmRental(notifications, eventProcessor, deadLettering),
sendReceipt(receipts, eventProcessor, deadLettering),
requestService(eventProcessor),
```

`main.ts` writes the function anonymously, as it does `eventProcessor`, by applying Kronos's `deadLettering` to the application's dead-letter queue, here the one in Postgres:

```ts
const handlers = [
  ...toolstore(
    (name) => eventProcessor(name, eventStore, postgresTokenStore(pg), postgresUnitOfWork(unitOfWork, pg)),
    (processor, sequence) => deadLettering(processor, postgresDeadLetterQueue(pg), sequence),
  ),
]
```

An automation sends its commands as itself. When `main.ts` adds `correlatingHandler` to the wrappers every handler shares, a command carries the correlation of the rental that caused it, so a trace or a log line leads from the receipt back to the request that rented the tool. [Interception and validation](/docs/kronos-ts/interception-and-validation) and [Observability](/docs/kronos-ts/observability) describe correlation and logging. Log through `ctx.log` only what the events do not record, such as the outcome of a call.

## Checking it works

Each slice's tests pass a client that records each call. The notifications test checks that a rental calls the system once. The receipts tests check that a rental sends the command, which calls the system and records `ReceiptSent`, and that neither the event nor the command handled again calls it a second time. The service tests check that the tenth rental requests a service, that the ninth does not, that the count starts again after a request, and that the command sent again appends nothing:

```sh
bun test src/guides/automations
```

```text title="Output"
 0 fail

```
