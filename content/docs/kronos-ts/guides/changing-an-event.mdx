---
title: Change an event's shape
description: Add a field to ToolAdded with an upcast so that events already in the log stay readable, and invalidate the snapshots that the change affects.
---

By the end of this guide `ToolAdded` carries a `category`, new events are written with it, and the events that were stored before the change still load, because they are converted to the new shape every time they are read. You need an application that already has `ToolAdded` events in its log, such as the tool store from the previous guides, and an event store that you can wrap.

The log is never rewritten. An **upcast** converts a stored event when the event store returns it, for every reader, as described on [Versioning](/docs/kronos-ts/versioning).

## Declare both versions

An event descriptor has a `version` that defaults to `"1.0"`, and the version is stored with each event. Describe the shape that the log holds today as a descriptor of its own, with the same name and its current version. Then change the descriptor that the application uses, give it the new version and add the field.

```ts
export const ToolAddedV1 = ns.event("ToolAdded", {
  version: "1.0",
  payload: z.object({ toolId: z.string(), model: z.string(), name: z.string() }),
  tags: { toolId: (payload) => payload.toolId },
})
```

```ts
export const ToolAdded = ns.event("ToolAdded", {
  version: "2.0",
  payload: z.object({ toolId: z.string(), model: z.string(), name: z.string(), category: z.string() }),
  tags: { toolId: (payload) => payload.toolId },
})
```

Both descriptors have the qualified name `toolstore.ToolAdded`. `ToolAddedV1` exists only so that the upcast can start from the old version and type its payload. Nothing appends or handles it. The `AddTool` command gains the same `category` field, so that `ctx.append(ToolAdded, payload)` has a value for it.

## Declare the upcast

`upcast(from, to, map)` declares a step from one descriptor to another. `map` receives the stored payload, typed as the payload of `from`, and returns the payload of `to`. The store sets the name and the version of the event from `to`. An event that no upcast is declared from is returned as it is.

```ts
export const categoryAdded = upcast(ToolAddedV1, ToolAdded, (payload) => ({ ...payload, category: "uncategorised" }))
```

The value `"uncategorised"` is a business decision: the category of a tool that was added before categories existed. Every old event reads as that value from now on. An upcast changes the payload and the version, not what the event is found by: its tags were written when it was appended.

## Wrap the event store

`upcastingEventStore(store, upcasts)` returns a store that applies the upcasts to everything it reads, for command handlers and processors alike. Wrap the store once and give the wrapped store to every command handler entry and every processor.

```ts
const eventStore = upcastingEventStore(inMemorySnapshottingEventStore(log), [categoryAdded])
```

When the store is also a snapshotting store, put the upcasting wrapper outermost, as above. With Postgres that reads `upcastingEventStore(postgresSnapshottingEventStore(postgresEventStore(pg), pg, serializer), [categoryAdded])`. Then the handlers and the processor use the new shape with no other edit.

```ts
const inventoryView = eventProcessor("inventory-view", eventStore, inMemoryTokenStore(), unitOfWork)
```

## Check the snapshot keys

A snapshot is a cached state, stored under a key that you choose. Upcasting converts events, not cached states, so a snapshot folded before the change is not converted. The `Tool` state was cached under `"tool-v1"` and now reads `category`, so raise its key to `"tool-v2"`. The next load folds the events again through the upcast.

```ts
  "tool-v2",
  afterEvents(100),
```

Raise the key whenever the change touches what a state computes. A state that does not read the changed event needs no new key.

## Change the event again

The next change adds a `ToolAddedV2` descriptor for the shape from this guide and a new current version. Declare a second upcast from `ToolAddedV2` to the new descriptor and list it beside the first: `upcastingEventStore(store, [categoryAdded, latestUpcast])`. An event written at 1.0 goes through both steps, whatever order they are listed in.

## Checking it works

`app.ts` writes two `ToolAdded` events in the 1.0 shape straight into an in-memory log, wraps the log, adds a third tool through the command, and reads the inventory:

```sh
bun run app.ts
```

```text title="Output"
t-1  Cordless drill  uncategorised
t-2  Tile saw        uncategorised
t-3  Table saw       saws
```

The script then reads the events of `t-1` from the unwrapped log and from the wrapped store. The log holds the event as it was written, and the store returns it converted:

```text title="Output"
stored  1.0  {"toolId":"t-1","model":"DCD791","name":"Cordless drill"}
read    2.0  {"toolId":"t-1","model":"DCD791","name":"Cordless drill","category":"uncategorised"}
```
