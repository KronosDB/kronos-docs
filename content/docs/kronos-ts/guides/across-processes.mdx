---
title: Split across processes
description: Run the tool store's command slices in one process and its inventory slice in another, each process calling only its slice functions, connected through KronosDB or RabbitMQ.
---

When you are done, the tool store runs as two processes built from the same code. One runs the command slices and appends events, the other runs the inventory slice: its projection and its query handler. A third script, which runs no slices, sends commands to the first and queries to the second. You need the slice layout from [Organize an app into slices](/docs/kronos-ts/guides/slices), a Postgres database for the read model, and either a KronosDB server with a context named `toolstore` ([Run on KronosDB](/docs/kronos-ts/guides/running-on-kronosdb) starts one) or a RabbitMQ broker.

A slice is a function returning its handlers, so a process is the same composition as `main.ts`, over the slices it calls. The processes share one event log and are connected by their buses.

| Process | Slices | Needs |
| --- | --- | --- |
| `commands.ts` | `addTool`, `registerCustomer`, `rentTool` | The event store and the buses. |
| `views.ts` | `inventory` | The event store, the buses and the read-model database. |
| `client.ts` | None. It sends `AddTool` and `GetInventory`. | The buses. |

## Connect to the infrastructure

Each process opens its infrastructure in one function, `connect`, so the process files do not reference the transport. `connect` returns the event store and the buses, the function the slices receive as `eventProcessor`, the pool, and the functions that start and close the connections:

```ts
eventProcessor: (name: string) =>
  eventProcessor(name, eventStore, postgresTokenStore(pg), postgresUnitOfWork(unitOfWork, pg)),
pg,
start: () => kdb.start(),
```

Every version keeps the read model, the processors' positions and the dead letters in Postgres, as in [Run on Postgres](/docs/kronos-ts/guides/running-on-postgres). Pick the transport you run for the rest.

<Tabs items={["KronosDB", "RabbitMQ"]}>
<Tab value="KronosDB">

KronosDB carries the events, the commands and the queries, so one connection builds the event store and both buses. `componentName` identifies each process to the server. Both sides use the same bus name, `toolstore`, which is the namespace commands and queries are routed in.

```ts
const kdb = await kronosDbConnection({
  host: process.env.KRONOSDB_HOST ?? "localhost",
  port: Number(process.env.KRONOSDB_PORT ?? 50051),
  context: "toolstore",
  componentName,
  serializer: jsonSerializer(),
})
```

```ts
const eventStore = kronosDbEventStore(kdb, "toolstore")
```

```ts
commandBus: localFirstCommandBus(kronosDbCommandBus(localCommands, kdb, "toolstore"), localCommands),
queryBus: localFirstQueryBus(kronosDbQueryBus(localQueries, kdb, "toolstore"), localQueries),
```

</Tab>
<Tab value="RabbitMQ">

RabbitMQ carries commands and queries and stores no events, so the event store is Postgres too, and the command bus takes the Postgres unit of work. `serviceName` is shared by every replica of one deployment, and `instanceId` must be different for every running process, because the reply queues are named from it.

```ts
const rabbit = await rabbitMqConnection(process.env.RABBITMQ_URL ?? "amqp://localhost", {
  serviceName,
  instanceId: crypto.randomUUID(),
})
```

```ts
const eventStore = postgresEventStore(pg)
```

```ts
commandBus: localFirstCommandBus(rabbitMqCommandBus(localCommands, rabbit), localCommands),
queryBus: localFirstQueryBus(rabbitMqQueryBus(localQueries, rabbit), localQueries),
```

</Tab>
</Tabs>

Both versions build the local buses first, and the transport buses wrap them. `start()` resolves once the other side has acknowledged this process's handlers, so call it after `kronos()` and before the process takes traffic. The options of each transport are on [Infrastructure](/docs/kronos-ts/infrastructure).

## Run the command slices

The commands process calls its three command slices. Its command handler list is the sum of their lists, and it has no processor, because none of its slices has an event handler:

```ts
const infrastructure = await connect("tool-commands")
const { eventStore, commandBus, queryBus } = infrastructure

// This process runs the command slices: its list is the sum of theirs.
const app = kronos({
  commandHandlers: [
    ...addTool().commandHandlers,
    ...registerCustomer().commandHandlers,
    ...rentTool().commandHandlers,
  ].map((handler) => ({
```

The rest of the file is the composition from [Organize an app into slices](/docs/kronos-ts/guides/slices#compose-in-maints): every handler wrapped and given the infrastructure from `connect`. A process that has no query or event handlers leaves those lists out. Then the process starts its connection with `await infrastructure.start()`.

## Run the inventory slice

The views process calls the inventory slice with the `eventProcessor` from `connect`, and composes its handlers in the same way. The slice builds its `inventory-view` processor, which reads every event the commands process appends:

```ts
const inventoryView = inventory(infrastructure.eventProcessor)
```

The processor's position is in Postgres, so after a restart the views process resumes where it stopped. A second views process on the same database shares the processor's segments with the first, as described in [Event processors](/docs/kronos-ts/event-processors).

## Send from a process without slices

The client opens the same infrastructure and calls no slices, so its `send` and `query` calls go to the other processes:

```ts
const infrastructure = await connect("tool-client")
await infrastructure.start()
const { commandBus, queryBus } = infrastructure
```

```ts
await send(commandBus, AddTool, { toolId: "t-1", model: "DCD791", name: "Cordless drill" })
await send(commandBus, AddTool, { toolId: "t-2", model: "D24000", name: "Tile saw" })
```

The inventory is written after the command returns, so the script polls the query until both tools are there:

```ts
const tools = await waitFor(
  () => query(queryBus, GetInventory, {}),
  (rows) => rows.length === 2,
)
```

## Local-first buses

Every process in this guide wraps its transport bus in `localFirstCommandBus` or `localFirstQueryBus`. A message whose handler is in the same process is handled in memory, without a trip to the server or the broker. Any other message goes through the transport to whichever process handles it. A subscription query always goes through the transport bus.

When every instance runs every slice, as several replicas of one process do, leave the command bus without `localFirstCommandBus`. Each command is then handled by the instance that received the request, and the server or the broker never spreads commands over the replicas. Queries stay local-first, because every replica reads the same tables.

## When no instance handles a message

If no process has registered a handler for a command or query name, the `send` or `query` call rejects with a `NoHandlerError`. Test for it with the `isNoHandler` guard instead of `instanceof`, so it also matches an error that arrived over the wire. The client uses it to report which process is missing:

```ts
} catch (error) {
  if (!isNoHandler(error)) throw error
  console.error("no process handles AddTool: is the commands process running?")
  process.exit(1)
}
```

What counts as no handler depends on the transport. KronosDB fails the call immediately when no connected client has subscribed to the name. With RabbitMQ, a name that no process has ever subscribed fails with `NoHandlerError`, but a name whose queue exists and has no consumer waits until the bus timeout (30 seconds by default) and then fails with an `UnavailableError`, which `isUnavailable` recognises.

A command that no process received changed nothing, so an edge can return 503 and the client can send it again once the process is back. A request that was sent and received no response may have taken effect. The tool store's commands accept being sent twice, as described in [Refuse a command](/docs/kronos-ts/guides/refusing-a-command#accept-a-command-sent-twice), so the client sends the same command again.

## Checking it works

Start the commands process and the views process, each in its own terminal, and wait for each to print that it is ready:

```sh
bun run commands.ts
```

```text title="Output"
commands process ready
```

```sh
bun run views.ts
```

```text title="Output"
views process ready
```

Set `DATABASE_URL` for each process, and with KronosDB on another host or port set `KRONOSDB_HOST` and `KRONOSDB_PORT`. With RabbitMQ, import `./rabbitmq-infrastructure` instead of `./kronosdb-infrastructure` in the three process files and set `RABBITMQ_URL`. Once both processes are ready, run the client, which sends both commands and prints the inventory:

```sh
bun run client.ts
```

```text title="Output"
t-1  Cordless drill  available
t-2  Tile saw        available
```

Stop the commands process with Ctrl-C and run the client again. With KronosDB it prints `no process handles AddTool` at once. With RabbitMQ it waits for the bus timeout and then throws an `UnavailableError`, because the queue for `AddTool` exists and has no consumer.
